# Архитектура PoC-рации — этап 1

## 1. Назначение каркаса

Приложение демонстрирует основу Push-to-Talk поверх IP-сети: QML-интерфейс,
отдельную C++-логику, сигнализацию по TCP и три состояния рации.
Передача звука пока не реализована. `AudioController` — намеренная заглушка,
а не имитация готового аудиотракта.

## 2. Разделение ответственности

```text
┌─────────────────────────────────────────────────────┐
│ QML: qml/PocRadio.qml + pages/MainPage.qml           │
│ Поля подключения, PTT, журнал, обложка, KeepAlive    │
└──────────────────────┬──────────────────────────────┘
                       │ Q_PROPERTY / Q_INVOKABLE / сигналы
┌──────────────────────▼──────────────────────────────┐
│ RadioState                                           │
│ Автомат IDLE/LISTENING/TRANSMITTING, правила эфира,  │
│ реакция на сворачивание и ответы сервера             │
└────────────────┬───────────────────────┬─────────────┘
                 │                       │
┌────────────────▼───────────┐ ┌─────────▼─────────────┐
│ SignalingClient            │ │ AudioController        │
│ TCP, буфер строк, протокол │ │ Заглушки приёма/передачи│
│ JOIN/PTT/SPEAKER/USERS     │ │ Точки для Opus/UDP      │
└────────────────────────────┘ └────────────────────────┘
```

- **QML** не разбирает сетевые пакеты и не принимает решения о праве говорить.
- **RadioState** не знает о кнопках, страницах и Silica, поэтому тестируется без GUI.
- **SignalingClient** только передаёт текстовые команды и разбирает поток на строки.
  TCP не сохраняет границы сообщений, поэтому накопительный буфер обязателен.
- **AudioController** изолирует будущую работу с микрофоном, кодеком и динамиком.

## 3. Состояния

| Состояние | Смысл в этом приложении | Аудио | Блокировка сна |
|---|---|---|---|
| `IDLE` | Вне канала, сеанс не активен | Выключено | Нет |
| `LISTENING` | В канале: эфир свободен, идёт приём или ожидается ACK | Приём только при чужом говорящем | Только при чужой передаче |
| `TRANSMITTING` | Сервер выдал нам эфир | Передача (пока заглушка) | Да |

Описание `IDLE` в задании относится к энергосбережению узла. В каркасе это
переведено на уровень приложения: вне канала освобождаются принадлежащие ему
аудиоресурсы и не запрашиваются keep-alive-блокировки. Управлением радиомодуля
и мобильным модемом занимается ОС, а не это приложение.

### Основные переходы

```text
                JOIN / ACK JOINED (или локальная симуляция)
       IDLE ───────────────────────────────────────────────► LISTENING
         ▲                                                   │  ▲  │
         │                                                   │  │  │ ACK PTT_GRANTED
         │ LEAVE / потеря соединения                         │  │  ▼
         └───────────────────────────────────────────────────┘  TRANSMITTING
                                                            │     ▲
                                                            │     │
                                              PTT_STOP/отпускание/сворачивание
```

`PTT_START` сам по себе не переводит приложение в `TRANSMITTING`: пока сервер
не ответил `ACK PTT_GRANTED`, остаётся `LISTENING` с признаком `pttPending`.
Это исключает ложное сообщение «говорите» при занятом эфире.

## 4. Правило «говорит только один»

Правило обеспечивается двумя независимыми уровнями:

1. **Сервер — источник истины.** У каждого канала только один `speaker`.
   `mock_server.py` выдаёт эфир первому `PTT_START`, остальным возвращает
   `ERROR BUSY <имя>`. Локальная проверка не заменяет серверную арбитрацию.
2. **Клиент защищает UX и ресурсы.** PTT недоступна при чужом `SPEAKER`,
   повторный запрос не отправляется во время ожидания, аудиопередача начинается
   только после подтверждения.

Дополнительно обрабатываются граничные случаи:

- отпускание до получения `PTT_GRANTED` отменяет запрос; поздний grant отклоняется
  повторным `PTT_STOP`, а повторное нажатие блокируется до очистки отмены;
- отпускание, отмена касания и сворачивание освобождают эфир;
- имя канала не может содержать пробельные символы (простой протокол `JOIN`
  их не экранирует), а учебный сервер отклоняет повторное имя участника в канале
  ошибкой `ERROR NAME_TAKEN`;
- разрыв соединения останавливает аудио и возвращает `IDLE`;
- противоречивое сообщение о другом говорящем останавливает локальную передачу;
- после `LEAVE` и в `IDLE` не остаётся активных аудиозаглушек.

## 5. Жизненный цикл: Active, сворачивание и Frozen

Это разные уровни, которые не следует смешивать:

- **Active/Inactive** — состояния GUI. В QML доступно
  `Qt.application.state === Qt.ApplicationActive`. В C++ используется сигнал
  `QGuiApplication::applicationStateChanged`.
- **Frozen/приостановка** — система может остановить выполнение фонового процесса.
  Это не отдельное перечисление `RadioState` и не универсальное QML-свойство.
  При замороженном процессе его код, включая обработку TCP, не выполняется.

В `src/main.cpp` на изменение GUI-состояния подписан `RadioState`:

- при сворачивании активная передача безопасно завершается;
- выбранный канал и объекты приложения не пересоздаются, поэтому обычное
  сворачивание/разворачивание не сбрасывает UI;
- при возврате PTT снова доступна, если эфир свободен;
- обложка показывает текущее состояние.

**Ограничение этапа:** постоянный приём в замороженном фоновом процессе не
гарантируется. Для него позднее нужно отдельно спроектировать фоновую часть,
политику энергопотребления, переподключение и уведомления. Нельзя считать
`KeepAlive` универсальной гарантией выполнения произвольного UI-процесса в фоне.

## 6. Keep-alive вместо непубличного LockManager

В документации Aurora SDK 5.2.1 отсутствует описанный публичный `LockManager`
с `keep-locks`. Документированный пользовательский API — `Nemo.KeepAlive 1.2`:

```qml
KeepAlive {
    enabled: radio.keepAlive
}

DisplayBlanking {
    preventBlanking: applicationWindow.applicationActive
                     && radio.mode === RadioState.Transmitting
}
```

- `KeepAlive.enabled` просит систему не приостанавливать устройство.
- `DisplayBlanking.preventBlanking` предотвращает гашение экрана, если это
  разрешено системной политикой.
- Оба механизма включены только там, где это нужно текущему сеансу.
  Постоянная блокировка в пассивном `LISTENING` привела бы к лишнему расходу
  батареи.

Официальные источники:

- [Энергопотребление и wake locks](https://developer.auroraos.ru/doc/5.2.1/platform/architecture/energy_consumption)
- [QML-тип KeepAlive](https://developer.auroraos.ru/doc/5.2.1/software_development/reference/system_utils/keepalive/all-types/keepalive)
- [QML-тип DisplayBlanking](https://developer.auroraos.ru/doc/5.2.1/software_development/reference/system_utils/keepalive/all-types/displayblanking)
- [Qt.application.state вместо устаревшего applicationActive](https://developer.auroraos.ru/doc/5.2.1/software_development/reference/interface_and_interaction/silica/obsolete-members/applicationwindow_obsolete)

## 7. Следующий аудиоэтап

Предлагаемый тракт, который должен остаться скрытым за `AudioController`:

```text
Микрофон → PCM → Opus → UDP/RTP → сеть
Сеть → UDP/RTP → jitter buffer → Opus → PCM → динамик
```

TCP-канал сигнализации передаёт только управление: вход, запрос/освобождение
эфира и `SPEAKER`. Медиапоток целесообразно отделить. Для реальной работы через
мобильную сеть понадобятся доступный сервер, таймауты, переподключение,
аутентификация, шифрование, контроль потерь и NAT/firewall-настройки.
Текущий текстовый TCP-протокол предназначен только для локального обучения.

При добавлении реального аудио в `.desktop` потребуется пересмотреть разрешения
`Audio` и `Microphone`, а в `.pro`/`.spec` — зависимости выбранного аудио-API.

## 8. Проверки этапа

`tests/tst_radiostate.cpp` проверяет:

1. начальный `IDLE` и отсутствие активных ресурсов;
2. цикл `LISTENING → TRANSMITTING → LISTENING`;
3. запрет второго говорящего и включение приёма;
4. завершение передачи при сворачивании;
5. освобождение ресурсов при выходе из канала;
6. запрет пробелов в имени канала;
7. реальный TCP-сценарий с grant, поздним grant, `ERROR BUSY`, повторным PTT
   и разрывом соединения.

Ручной сценарий в симуляции:

1. Войти в канал — получить `LISTENING`.
2. Удерживать PTT — получить `TRANSMITTING`; отпустить — `LISTENING`.
3. Включить имитацию входящей передачи — PTT блокируется.
4. Во время своей передачи свернуть приложение — на обложке должно остаться
   `LISTENING`, а не `TRANSMITTING`.
5. Выйти из канала — получить `IDLE`.
